보안 감사 리포트 — Forkcast DeFi 컨트랙트

감사일: 2026-05-20
감사자: solidity-auditor (Claude Code)
저장소: forkcast-defi/contracts/
브랜치: fix/web-state-history-ui

요약

contracts/src/의 프로덕션 솔리디티 소스 파일에 대한 전문 보안 감사를 수행했습니다. 이 코드베이스는 Aave v3와 Uniswap v4를 결합한 초기 단계의 DeFi 모노레포입니다. 다수의 Critical 및 High 심각도 취약점이 발견됐습니다. 가장 심각한 취약점은 외부 공격자가 모든 사용자 스마트 계정을 완전히 제어하고 자금을 탈취할 수 있게 합니다. 메인넷 배포 전에 반드시 해결해야 합니다.

AccountFactory의 두 가지 Critical 취약점(C-01, C-02)은 배포 전 필수 해결 항목입니다. 해결 전까지 시스템에 사용자 자금이 유입되어서는 안 됩니다.

[C-01] AccountFactory.setRouter에 접근 제어 없음 — 누구나 라우터를 탈취 가능

심각도: Critical
위치: src/factory/AccountFactory.sol:12-14

설명:

address public router;

function setRouter(address _router) external {   // ← 접근 제한 없음
    router = _router;
}

function createAccount(address user) external returns (address) {
    address account = address(new UserAccount());
    UserAccount(payable(account)).initialize(user, router);  // router가 계정에 고정됨
    accountOf[user] = account;
    return account;
}

setRouter에 onlyOwner 등의 접근 제한이 없습니다. 여기서 저장된 router 주소는 모든 UserAccount에 유일한 권한 게이트(onlyRouter)로 주입됩니다. UserAccount.execute(H-01)는 라우터가 계정 내부에서 임의의 외부 호출을 실행하도록 허용합니다. 따라서 계정 생성 시점에 router를 제어하는 주체가 그 계정의 자금을 영구적으로 제어하게 됩니다.

공격 시나리오:

  1. 공격자가 factory.setRouter(attackerContract)를 호출합니다.
  2. 피해자 또는 운영자가 factory.createAccount(victim)를 호출합니다. 새 계정은 router = attackerContract로 초기화됩니다.
  3. 피해자가 새로 생성된 계정에 토큰을 예치합니다.
  4. 공격자가 attackerContract를 통해 userAccount.execute(USDC, 0, abi.encodeCall(IERC20.transfer, (attacker, balance)))를 호출해 계정을 탈취합니다.

권고 수정 방법:

router를 immutable로 선언하고 생성자에서 설정합니다. 가변성이 필요한 경우 접근 제어와 타임락을 추가합니다:

contract AccountFactory {
    address public immutable router;
    address public immutable owner;

    constructor(address _router) {
        router = _router;
        owner = msg.sender;
    }
}

참고: SWC-105 (보호되지 않은 Ether 인출), SWC-118 (잘못된 생성자)

[C-02] createAccount 매핑 덮어쓰기 가능, 라우터 신뢰가 오너 승인 없이 설정됨

심각도: Critical
위치: src/factory/AccountFactory.sol:16-21, src/accounts/UserAccount.sol:38-43

설명:

accountOf[user] = account는 조건 없이 덮어씁니다. createAccount(victim)을 두 번 호출하면 기존 계정의 매핑 항목이 덮어써지고, 원래 계정에 보관된 자금이 고립됩니다. 공격자는 임의의 user 주소에 대해 이를 자유롭게 호출할 수 있습니다. C-01과 결합하면 계정의 router 값은 공격자가 설정한 값이 되어 계정 오너의 승인 없이 결정됩니다.

공격 시나리오:

  1. 피해자의 계정에 자금이 예치되어 있고 accountOf[victim]이 account_A를 가리킵니다.
  2. 공격자가 createAccount(victim)을 호출(퍼미션리스)합니다. accountOf[victim]이 이제 account_B(비어있고 공격자 라우터)를 가리킵니다.
  3. 프론트엔드/인덱서가 accountOf[victim]으로 피해자의 계정을 조회합니다. 새로운 예치금이 account_B로 흘러 들어가고 공격자가 이를 탈취합니다.

권고 수정 방법:

재생성을 방지하고 CREATE2를 사용해 결정론적 주소를 생성합니다:

function createAccount(address user) external returns (address) {
    require(accountOf[user] == address(0), "already exists");
    address account = address(
        new UserAccount{salt: keccak256(abi.encode(user))}()
    );
    UserAccount(payable(account)).initialize(user, router);
    accountOf[user] = account;
    return account;
}

사용자 본인만 계정을 생성할 수 있도록 msg.sender == user 체크도 추가를 권장합니다.

참고: SWC-118, SWC-114 (트랜잭션 순서 의존성)

[H-01] UserAccount.execute가 재진입 방어 없는 범용 임의 호출 프리미티브

심각도: High (C-01/C-02 미해결 시 Critical)
위치: src/accounts/UserAccount.sol:55-64

설명:

function execute(address target, uint256 value, bytes calldata data)
    external onlyRouter returns (bytes memory)
{
    (bool success, bytes memory result) = target.call{value: value}(data);
    require(success, "call failed");
    return result;
}

이것은 완전히 범용적인 "무엇이든 호출" 프리미티브입니다. 모든 사용자 자금의 보안 모델이 "라우터를 신뢰할 수 있는가?"로 귀결됩니다. C-01/C-02에 의해 현재 라우터는 배포 시점에 공격자가 제어할 수 있습니다.

정직한 라우터라도 재진입 방어가 없습니다. 악의적인 ERC777 토큰이나 훅 조작 풀이 잔액이 정산되기 전에 execute나 withdraw로 재진입할 수 있습니다.

프로젝트에는 이미 현재 미사용 중인 TStore.sol(EIP-1153 트랜지언트 스토리지)이 있습니다 — 여기가 자연스러운 활용처입니다.

권고 수정 방법:

  • 범용 execute를 타입화된 함수로 교체합니다: supply(asset, amount), borrow(asset, amount), swap(...) — 각각 신뢰된 대상 주소를 하드코딩
  • 범용 프리미티브를 유지한다면 대상을 허용 목록(Aave 풀, PoolManager)으로 제한합니다
  • 기존 TStore 라이브러리를 활용해 재진입 방어를 추가합니다:
bool private _entered;
modifier nonReentrant() {
    require(!_entered, "reentrant");
    _entered = true;
    _;
    _entered = false;
}

참고: SWC-107 (재진입), SWC-105

[H-02] SwapPriceLoggerHook._readSlot0이 잘못된 스토리지 슬롯을 읽음 — 가격 데이터 손상

심각도: High
위치: src/hook/SwapPriceLoggerHook.sol:88-98

설명:

function _readSlot0(bytes32 poolId) internal view returns (uint160 sqrtPriceX96, int24 tick) {
    bytes32 slot = keccak256(abi.encode(poolId, uint256(6)));  // 잘못됨
    bytes32 raw = poolManager.extsload(slot);
    sqrtPriceX96 = uint160(uint256(raw));
    tick = int24(int256(uint256(raw) >> 160));
}

정확한 v4 슬롯 유도 방법 (StateLibrary._getPoolStateSlot에서 확인):

keccak256(abi.encodePacked(poolId, bytes32(uint256(6))))  // POOLS_SLOT = 6

잘못된 유도로 인해 extsload가 잘못된 슬롯의 값(주로 0 또는 무관한 데이터)을 반환합니다. 모든 PriceLogged 이벤트와 latestObservation[poolId] 항목이 실제 풀 가격이 아닌 잘못된 값을 기록합니다. 인덱서, 프론트엔드 차트, 또는 미래에 이 데이터를 기반으로 포지션을 조정하는 전략이 손상된 값을 받게 됩니다.

권고 수정 방법:

StateLibrary를 직접 사용합니다. 슬롯 계산을 직접 작성하지 않습니다:

import {StateLibrary} from "v4-core/src/libraries/StateLibrary.sol";
import {PoolId, PoolIdLibrary} from "v4-core/src/types/PoolId.sol";

using StateLibrary for IPoolManager;
using PoolIdLibrary for PoolKey;

function _afterSwap(
    address,
    PoolKey calldata key,
    IPoolManager.SwapParams calldata,
    BalanceDelta,
    bytes calldata
) internal override returns (bytes4, int128) {
    (uint160 sqrtPriceX96, int24 tick,,) = poolManager.getSlot0(key.toId());
    // ... 나머지 스토리지 로직
}

_readSlot0과 _getCurrentPrice를 삭제합니다. 스왑 후 latestObservation[poolId].sqrtPriceX96 == poolManager.getSlot0(id).sqrtPriceX96를 검증하는 테스트를 추가합니다.

참고: v4 StateLibrary, SWC-110

[H-03] SafeCast.toInt128 하한 체크 누락 — 부호 있는 캐스팅 묵인

심각도: High
위치: src/libs/SafeCast.sol:14-17

설명:

function toInt128(int256 x) internal pure returns (int128) {
    if (x > type(int128).max) revert Overflow();   // 상한만 체크
    return int128(x);                               // x < type(int128).min은 묵인
}

type(int128).min - 1 값이 체크를 통과하고 잘못된, 잠재적으로 공격자에게 유리한 값으로 묵인됩니다. Uniswap v4 델타는 부호 있는 정수이며 음수가 빈번하므로, toInt128을 음수 델타에 호출하는 미래의 스왑 정산 코드가 정산 금액을 잘못 계산할 수 있습니다.

권고 수정 방법:

function toInt128(int256 x) internal pure returns (int128) {
    if (x > type(int128).max || x < type(int128).min) revert Overflow();
    return int128(x);
}

직접 작성한 버전 대신 OpenZeppelin SafeCast 또는 v4-core SafeCast 채택을 권장합니다.

참고: SWC-101 (정수 오버플로우/언더플로우)

[M-01] AccountFactory.createAccount에 기존 계정 덮어쓰기 방지 장치 없음

심각도: Medium
위치: src/factory/AccountFactory.sol:16-21

설명: C-02의 라우터 신뢰 문제와 별개로, require(accountOf[user] == address(0)) 부재는 독립적인 그리핑(griefing) 벡터입니다. 누구나 매핑 항목을 덮어써 자금이 예치된 계정을 고립시킬 수 있습니다. 이전 계정의 자금은 사라지지 않지만(기존 컨트랙트에 남아있음) 팩토리를 통해 접근할 수 없게 됩니다.

권고 수정 방법: createAccount 첫 줄에 require(accountOf[user] == address(0), "account exists")를 추가합니다.

[M-02] UserAccount가 raw IERC20.transfer/approve 사용 — 비표준 토큰에서 오작동

심각도: Medium
위치: src/accounts/UserAccount.sol:71, 80

설명:

IERC20(token).approve(spender, amount);   // 반환값 무시
IERC20(token).transfer(owner, amount);    // 반환값 무시

실패 시 false를 반환하는 일부 레거시 토큰은 묵인됩니다. 데이터를 반환하지 않는 토큰(메인넷 USDT)은 ABI 디코딩에서 revert됩니다. USDT 방식 토큰의 승인 호출은 먼저 0으로 리셋이 필요한데 이를 처리하지 않습니다. 커스터디 컨트랙트에서 이는 자금이 실제로는 이동하지 않았는데 로직이 성공으로 간주하는 상황을 만들 수 있습니다.

권고 수정 방법: SafeERC20의 safeTransfer, forceApprove로 교체합니다.

참고: SWC-104 (미확인 호출 반환값)

[M-03] Miniv4SwapRouter 슬리피지 체크가 부호 추론에 의존; deadline 파라미터 없음

심각도: Medium
위치: src/uniswapV4/Miniv4SwapRouter.sol:100-104

설명:

uint256 amountOut = amount0 > 0 ? uint256(amount0) : uint256(amount1);
if (amountOut < cbData.minAmountOut) revert TooLittleReceived(...);

표준 스왑에서는 하나의 델타가 양수(출력)이므로 추론이 동작합니다. 그러나 afterSwapReturnDelta가 활성화된 훅을 사용하는 적대적 풀에서는 두 델타 모두 비양수가 될 수 있어 amountOut = uint256(음수_int256)이 매우 큰 숫자가 되어 슬리피지 체크를 항상 통과합니다.

deadline 파라미터도 없습니다. 멤풀에 묶인 트랜잭션이 만료 없이 오래된 가격으로 실행됩니다.

권고 수정 방법:

int256 out = params.zeroForOne ? amount1 : amount0;
require(out > 0, "no output");
if (uint256(out) < cbData.minAmountOut) revert TooLittleReceived(uint256(out), cbData.minAmountOut);

SwapParams에 uint256 deadline을 추가하고 require(block.timestamp <= deadline, "expired")를 적용합니다.

참고: SWC-114 (트랜잭션 순서 의존성 / 프론트런)
