# snapshot R4 긴 트랜잭션 / 부분 실패 처리 개선 정리

> 날짜: 2026-05-08
> 범위: `snapshot` job의 긴 트랜잭션과 부분 실패 처리 문제(`R4`) 정리

---

## 1. 이 문서의 목적

이 문서는 `snapshot` job의 `R4` 문제를 나중에 다시 설명하거나 면접에서 복기할 수 있도록 정리한 메모다.

정리하려는 질문은 아래와 같다.

- 어떤 문제가 있었는가
- 왜 문제가 되는가
- 처음 떠오를 수 있는 여러 해결책 중 왜 현재 방식을 택했는가
- 실제 코드를 어떻게 바꿨는가
- 어떻게 검증했는가

---

## 2. 어떤 문제가 있었나

기존 `snapshot` job은 다음 흐름으로 동작했다.

1. 오픈 포지션 전체 조회
2. 포지션마다 `StrategyLens` RPC 호출
3. `PositionSnapshot` 생성
4. 각 스냅샷을 DB에 저장

문제는 이 전체 흐름이 사실상 하나의 큰 트랜잭션 안에 있었다는 점이다.

즉:

- DB 조회
- 포지션별 RPC
- 개별 snapshot save

가 전부 한 트랜잭션으로 이어져 있었다.

---

## 3. 왜 위험했나

이 구조는 크게 두 가지 위험이 있었다.

### 3-1. 트랜잭션이 너무 오래 열린다

오픈 포지션 수가 늘어나면 포지션마다 RPC 호출을 해야 하므로 실행 시간이 계속 길어진다.

그 결과:

- DB connection을 오래 점유할 수 있다
- lock을 오래 쥔 채로 실행된다
- 실행 시간이 lease보다 길어질수록 운영 리스크가 커진다

즉 단순히 "느릴 수 있다"가 아니라, 긴 트랜잭션 자체가 운영 리스크였다.

### 3-2. RPC 하나 실패하면 앞에서 성공한 저장분도 같이 날아갈 수 있다

예를 들어 포지션 50개 중:

- 1~49번은 성공해서 save
- 50번에서 RPC 실패

라고 해도, 바깥 트랜잭션이 rollback되면 앞에서 저장한 49개도 같이 사라질 수 있었다.

즉 "하나 실패하면 전체 snapshot run이 실패"하는 구조였다.

---

## 4. 실제 실패 원인은 무엇이었나

이번 `R4`를 볼 때 중요한 포인트는, 문제의 핵심이 "RPC 호출 횟수가 많다" 그 자체만은 아니라는 점이다.

현재 코드에서 더 본질적인 문제는:

- for 루프 전체가 긴 트랜잭션 안에 있었다는 것
- 포지션별 실패를 loop 안에서 흡수하지 못했다는 것

즉 RPC가 느린 것도 문제지만,

**RPC 호출과 DB 쓰기가 같은 긴 트랜잭션에 묶여 있었기 때문에 실패 범위가 과도하게 커졌다**는 게 핵심이었다.

---

## 5. 처음 검토한 해결 방향들

`R4`를 보면서 몇 가지 선택지를 같이 검토했다.

### 5-1. 포지션마다 개별 커밋

장점:

- 하나 실패해도 앞에서 저장한 것은 남는다

단점:

- 트랜잭션 수가 너무 많아질 수 있다
- 현재 규모에 비해 복잡도가 커진다

### 5-2. 청크 커밋

장점:

- 부분 성공 보존 가능
- 포지션별 1커밋보다는 덜 잘게 나뉜다

단점:

- chunk 분할 로직이 추가된다
- 지금 규모에서는 방어 깊이에 비해 복잡도가 커질 수 있다

### 5-3. RPC 결과를 먼저 메모리에 모으고 마지막에 한 번에 저장

장점:

- RPC 구간을 트랜잭션 밖으로 뺄 수 있다
- DB 트랜잭션을 매우 짧게 만들 수 있다
- 코드가 단순하다
- 현재 오픈 포지션 규모에서는 메모리 부담이 거의 없다

단점:

- 마지막 save 단계에서 장애가 나면 성공 결과를 한 번에 잃을 수 있다

---

## 6. 왜 이번에는 "collect all + saveAll"을 택했나

이번 단계에서는 `collect all + saveAll`이 가장 현실적인 1차 해결책이라고 판단했다.

이유는 다음과 같다.

1. 현재 오픈 포지션 규모는 수십~수백 개 수준이라 메모리 부담이 크지 않다.
2. 실제로 더 빈번한 실패 원인은 DB write보다 RPC timeout일 가능성이 높다.
3. 이번 `R4`의 우선순위는 긴 트랜잭션 해소와 부분 실패 격리다.
4. 그 목표는 `collect all + saveAll`만으로도 충분히 달성할 수 있다.
5. chunk 커밋은 추가 방어를 주지만, 지금은 복잡도 증가가 더 커 보였다.

즉 이번 결정은 "청크가 틀렸다"가 아니라,

**현재 운영 규모에서는 더 단순한 구조로 먼저 문제를 해결하고, 나중에 필요하면 chunk로 확장하자**는 판단이었다.

---

## 7. 최종적으로 어떻게 바꿨나

핵심 아이디어는 간단하다.

### 7-1. `SnapshotService.run()` 전체 트랜잭션을 제거했다

기존에는 클래스 레벨 `@Transactional` 때문에 `run()` 전체가 하나의 긴 트랜잭션이었다.

이걸 제거해서:

- 오픈 포지션 조회
- 포지션별 RPC
- 메모리 수집

이 구간이 더 이상 긴 트랜잭션에 묶이지 않게 했다.

### 7-2. 포지션별 RPC 실패를 loop 안에서 흡수하게 바꿨다

각 포지션마다:

- RPC 성공 시 `PositionSnapshot` 생성 후 리스트에 추가
- RPC 실패 시 로그 남기고 실패 카운트 증가 후 `continue`

이렇게 바꿨다.

즉 하나 실패해도 전체 `snapshot` run이 즉시 중단되지 않게 만들었다.

### 7-3. DB 쓰기는 마지막 `saveAll()` 한 번으로 모았다

성공한 snapshot들만 메모리에 모아두고,
마지막에 `SnapshotWriteService.saveAll(...)`을 호출하게 바꿨다.

이 `saveAll()`만 별도 `@Transactional`로 처리하게 해서,

- DB write 구간은 짧고 명확한 트랜잭션
- RPC 구간은 트랜잭션 밖

구조가 되도록 했다.

---

## 8. 왜 `SnapshotWriteService`를 따로 만들었나

이 부분도 중요한 포인트다.

같은 `SnapshotService` 안에서:

```java
@Transactional
void saveAllSnapshots(...) { ... }
```

처럼 메서드만 하나 분리해도, 같은 클래스 내부 호출이면 스프링 프록시를 타지 않을 수 있다.

그래서 아예 별도 빈인 `SnapshotWriteService`를 만들어:

- `SnapshotService`는 orchestration 담당
- `SnapshotWriteService`는 write 트랜잭션 담당

으로 역할을 분리했다.

이렇게 해야 `@Transactional` 경계가 의도대로 동작한다.

---

## 9. 최종 구조는 어떻게 되었나

지금 구조를 흐름으로 쓰면 이렇다.

1. `snapshot` job 시작
2. 오픈 포지션 조회
3. for 루프에서 포지션별 개별 RPC 호출
4. 성공한 결과만 메모리 리스트에 적재
5. 실패한 포지션은 로그/카운트 후 계속 진행
6. 루프 종료 후 `saveAll(successSnapshots)`
7. `job_run`은 성공 처리
8. partial failure가 있으면 경고 로그로 남김

즉:

- 긴 트랜잭션 제거
- 부분 성공 허용
- 성공분은 한 번에 저장

구조로 바뀌었다.

## 11. 어떻게 검증했나

이번에는 `SnapshotServiceTest`를 추가해서 다음 시나리오를 검증했다.

### 시나리오

- 오픈 포지션 2개 준비
- 첫 번째 포지션 RPC는 성공
- 두 번째 포지션 RPC는 실패

### 기대 결과

1. snapshot job 전체는 실패하지 않는다
2. 성공한 포지션 1개는 `position_snapshot`에 저장된다
3. 실패한 포지션 때문에 앞쪽 저장분이 사라지지 않는다
4. `job_run`은 `FAILED`가 아니라 `SUCCESS`로 남는다

실행 명령:

```bash
./gradlew test --tests io.forkcast.backend.snapshot.service.SnapshotServiceTest
```

결과:

- 테스트 통과

## 12. 면접에서 짧게 말하면

짧게 설명하면 이렇게 말할 수 있다.

> 기존 snapshot job은 포지션별 RPC와 DB 저장이 한 긴 트랜잭션에 묶여 있어서, 하나의 RPC 실패가 앞에서 성공한 저장분까지 롤백시킬 수 있었습니다. 그래서 트랜잭션 범위를 write 구간으로만 줄이고, 포지션별 RPC 실패는 루프 안에서 흡수한 뒤 성공한 snapshot들만 메모리에 모아 마지막에 `saveAll` 하도록 바꿨습니다. 그리고 한 포지션 실패, 한 포지션 성공 시나리오에서 성공분이 실제로 저장되는 테스트로 검증했습니다.

---

## 13. 핵심 한 줄 요약

`snapshot`의 `R4`는 RPC 호출과 DB 쓰기가 같은 긴 트랜잭션에 묶여 실패 범위가 너무 크던 문제였고, 이를 **트랜잭션 밖 RPC 수집 + 마지막 saveAll 한 번** 구조로 바꿔 부분 실패를 허용하도록 개선했다.
